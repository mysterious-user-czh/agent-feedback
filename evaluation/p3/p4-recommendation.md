# P4 修正：产品集成与完整检测闭环

## 为什么修正

早期路线文档曾把 P4 简写为“MLflow／跨 engine／failproofai 扩展”，但用户的最终目标始终是：制作可复用的插件或 Skill，集成现有工具与自研能力，检测 Agent 的 Skill 是否选对、执行是否正确、任务是否真正完成。

因此，跨 engine 比较不是最终目标；它只是集成验证的一部分。P3 已完成检测内核，P4 应把内核接入真实工作流并交付可用产品。

## P4 目标形态

```text
真实 Agent 会话／隔离任务
        ↓
agent-feedback 插件／Skill／MCP
        ↓
任务切段＋技能选择＋工具结果＋独立产物验证＋退出码
        ↓
五维报告与失败证据
        ↓
生成可复现用例 → skill-up custom engine 回归
        ↓
配置／技能树／模型版本与结果存入 MLflow
        ↓
修复后同 case 回归，正常例防退化
```

## 四部分工作

### 1. 产品封装与真实接入（必须）

- 把现有核心、MCP 和报告封装为可复制安装的插件或 Skill，提供统一入口。
- 先接 Hermes，再选第二个 Agent 验证适配器可复用性；不是先追求跨 engine 排名。
- 真实接入先在隔离副本验证，再明确哪些能力能安全用于日常会话；未经用户许可不修改现有配置。
- 保留五维分账与 unknown；工具失败、最终产物和退出状态不能互相抵消。

### 2. skill-up custom engine 集成（必须）

- 使用已确认的 `engine.custom`，让 Hermes 能通过 local／http transport 参与同 harness 回归。
- 将失败任务转换为包含输入、fixture、期望和独立 oracle 的可复现用例。
- 确定性检查优先使用 `judge: script`；不为了迁移而放宽现有 oracle。
- 同 harness 结果与跨 engine 结果分开，不能把 Skill 内容可迁移误写成路由器可迁移。

### 3. MLflow 存证与版本比较（集成能力，不是检测前提）

- 记录配置、技能树、模型、数据版本及五维指标，支持修复前后同 case 对比。
- 原始消息、凭据、会话标识和绝对路径不进入跟踪服务，只保存脱敏指标和本地证据引用。
- MLflow 故障不应阻断本地采集和报告；核心工具必须可独立运行。

### 4. failproofai 的有限职责（按需）

- 其 PreToolUse 能力适合作为执行前拦截的隔离实验，不替代事后检测与归因。
- 不自动修改真实技能或生产路由；没有对照和回滚证据时不宣称改善。

## 最终验收

1. 在另一个干净 Agent 环境按文档安装插件／Skill，无需复制开发机配置。
2. 跑通至少一个真实任务，自动得到选择、工具结果、独立产物验证、退出码及五维报告。
3. 对一个真实失败生成 skill-up 用例并复现，再验证修复后的同 case 回归与正常例防退化。
4. MLflow 能按配置／技能树／模型版本找回对应脱敏结果，原始敏感数据零上传。
5. 全流程不修改未经批准的现有 Agent 配置，缺失能力明确显示 unknown。

只有以上闭环实际跑通，才能说完成了最初目标；57 项测试或第二个 engine 单独跑通都不算最终完成。
